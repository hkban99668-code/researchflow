## 0. 一句话

⑦ 校验不通过或某个节点报错时，不再直接结束，而是进入 `attribute` 节点：**能用规则确定的直接按规则回溯，规则确定不了的交给一个有预算上限的 ReAct Agent**。Agent 只有只读工具和两个决策工具（"回到某一步并改某个参数"或"转人工"），决定之后由图用 `Command(goto=...)` 执行回溯。

## 1. 为什么这样分层

Eval v1 已经给出答案：

| 组 | 纯规则归因准确率 |
| --- | --- |
| 单步故障（节点直接报错，错误码已经说明了原因） | 100% |
| 跨步骤故障（⑦ 发现 r2 低，但根因在 ③ 的数据） | 0% |
| 应转人工（数据本身没法修） | 0% |

所以：

- **节点报错 → 规则处理，不调 LLM。** 错误码和 `backtrack_to` 已经说明了原因，调模型只会多花钱、多一份不确定性。
- **⑦ 校验不通过 → Agent 处理。** 校验失败只是症状，`owner_step` 只说明"哪个节点负责这一项"，不说明"问题出在哪"。r2 低，可能是数据里有离群值（回到 ③ 能修），也可能是 y 整列都是噪声（谁也修不了）。区分这两种情况需要看数据，这才是 Agent 的价值所在。

面试时可以这样讲：规则优先、模型兜底；模型只在规则判断不了的地方出场。

## 2. 图的变化

```
validation ──(通过)──────────────────────────────► END
     │
     └──(不通过)──► attribute ──(回溯)──► Command(goto=目标节点, update=patch)
                       │
任一节点 error ────────┤
                       ├──(转人工)──► END（termination.kind = "escalated"）
                       └──(预算用尽)──► END（termination.kind = "budget_exhausted"）
```

- `route_next` 改为：`termination.kind == "error"` 时去 `attribute`，其他终止（rejected、empty）照旧去 END。
- 检索为空（empty）暂不进 `attribute`，留给以后的检索 Agent（R-5）。
- 回溯时清掉 `termination` 和 `error`，把 patch 写进参数，`attempt` 加 1。全局回溯次数超过 `max_total_backtracks`（默认 2）就以 `budget_exhausted` 结束。
- **回溯到 `data_prepare` 会重新经过 `data_review` 的人工审核。** 数据变了，人必须重新审，这是 T-007 的设计自然带来的效果，面试时可以说明 HITL 和 Agent 是怎么配合的。

## 3. 让"归因对了"也能真正恢复

Eval 审查时发现：就算 Agent 正确地把 y 离群值归给 `data_prepare`，③ 现在也没有可调的参数，回去重跑结果还是一样（B16）。所以 ③ 要加一个**默认关闭**的清洗参数：

- `params.cleaning.y_outlier_strategy`：`none`（默认）或 `iqr`（去掉 y 超出 `[Q1 − k·IQR, Q3 + k·IQR]` 的行，`k` 默认 3）。
- 默认值必须保证现有行为完全不变：T-006 的可复现测试、T-011 的 Eval 基线都不能动。

Patch 用 Pydantic 校验，只允许改白名单里的参数：

| 目标节点 | 允许的 patch |
| --- | --- |
| `data_prepare` | `cleaning.y_outlier_strategy`、`cleaning.y_outlier_k` |
| `compute` | `test_size`、`seed` |

Agent 不能直接改数据，也不能改规则阈值。理由是最小权限：改阈值等于把"考试不及格"改成"及格线降低"。

## 4. Agent 的工具

| 工具 | 类型 | 作用 |
| --- | --- | --- |
| `read_validation_report` | 只读 | 哪些检查没通过、负责节点是谁 |
| `read_step_error` | 只读 | 报错节点的错误码和消息 |
| `inspect_column` | 只读 | 某一列的分布摘要：分位数、均值、标准差、IQR 外的点数（只返回统计量，不返回原始行） |
| `read_compute_result` | 只读 | 指标、训练集和测试集大小 |
| `propose_backtrack` | 决策 | `target_step` + `patch` + `reason`，调用后回路结束 |
| `escalate_to_human` | 决策 | `reason`，调用后回路结束 |

- 复用 T-002 的注册表和 T-003 的 `run_tool_loop`。回路要增加"决策工具"的概念：模型调用决策工具时，回路立即结束，返回这次决策。
- 系统提示里写明（针对冒烟 C4）：工具返回错误时，要么修正参数重试，要么明确放弃并说明原因，不能忽略错误直接下结论。
- 预算：`max_steps=6`、`max_tool_calls=8`。

## 5. 评测怎么报

Eval 要同时报告这些数字，并且**分组报告**：

1. **归因准确率**：规则基线和 Agent 各一份，按单步、跨步骤、应转人工三组分别报告。
2. **自动恢复率**：回溯之后最终通过 ⑦ 的比例。只看归因准确率容易刷分，两个数一起看才可信。
3. **转人工的准确率和召回率**：该转的转了没有，不该转的有没有乱转。
4. **"规则直接处理 / 需要调用 LLM"的占比**、平均回溯次数、每条用例的 token 和耗时。

为了省额度，真实层评测时 ② ⑥ 继续用 Fake，**只有归因 Agent 调用真实模型**（`--llm-scope agent`）。估算每条走到 Agent 的用例约 8000 token，12 条约 10 万 token，在免费额度之内。这是估算，没有实测。

## 8. gu 确认后的细化（2026-10-10，写 T-014 卡时）

- gu 已确认 §7 的三点。
- **报错走规则，但规则的动作是"转人工"，不是"回溯"。** 写卡时发现：节点报错的情况（缺列、未知算法、缺失率超标）都没有可以调的参数，原样回到那一步重跑只会再错一次。所以规则层的决策是"诊断出问题在 `backtrack_to` 这一步，转人工"。这和 §1 的分层不冲突：仍然不调 LLM，只是动作更诚实。
- 因此评测要把**诊断**和**动作**分开：归因准确率看诊断出的步骤对不对，自动恢复率看动作有没有真的修好。单步故障在这个口径下仍然是"诊断正确、转人工"。
