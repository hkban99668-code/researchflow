## 2. 新发现的问题

1. **deepseek 在这个接口上并不执行 json_schema 约束，而我们在 json_schema 模式下把 schema 从 prompt 里拿掉了。** 两件事叠在一起，模型第一次根本不知道要输出什么字段，只能靠重试回喂的错误信息去猜。这正是之前担心的"静默失效"：接口返回 200，看起来一切正常。修法：json_schema 模式也在 prompt 里保留一份简短的字段说明，或者在启动时用一次探测请求判断 Provider 是否真的执行约束，不执行就自动降级为 json_object。这也给出了结构化输出的第一组真实数字：首轮合法率 qwen json_schema 3/3，deepseek json_schema 0/3，deepseek json_object 3/3（样本量很小，只能说明方向）。
2. **qwen 在 json_schema 模式下 token 和耗时都高出很多。** 同样输出一个 `ResearchQuestion`：json_schema 每次约 2500 个 completion token、约 29 秒；json_object 每次约 540 个 token、约 8 秒。输出的 JSON 本身只有一两百字，多出来的应该是模型的思考 token。按这个量，34 条 Eval 用例跑一轮真实层大约 20 万 token，在每个模型 100 万的免费额度内，但很浪费。下一步：查百炼文档里关闭思考模式的参数（例如 `enable_thinking`），做成可配置项，对比关闭前后的首轮合法率。这是推断，还没验证。
3. **② 提炼出的变量是编造的。** 真实运行中，`ResearchQuestion.variables` 是 `data_cleaning_strategy`、`missing_rate`、`regression_coefficient_bias` 这类名字，而数据集里只有 `x1/x2/x3/y`；初稿"方法"一节照搬了这些变量名，⑦ 照样判定通过。Fake 模式下看不到这个问题，因为 Fake 直接用课题里的列名构造输出。修法：在 ② 的 prompt 里给出真实的列名，并在 ⑦ 加一条硬规则"`variables` 必须是数据集列的子集"，与以后"引用必须来自检索结果"是同一个思路：把约束做在程序里，而不是只写在 prompt 里。
4. **S5 中两个模型对工具错误的反应不同。** 两个模型第一次调用 `check_data_quality` 都给错了路径（`invalid_args`）。deepseek 读了回填的错误，改了参数重试成功；qwen 没有重试，直接给出了结论。这说明"错误回填给模型"本身不够，归因 Agent 的系统提示里要明确要求：工具返回错误时必须修正后重试，或者明确放弃并说明原因。这类行为差异要进 Eval 的真实层。
