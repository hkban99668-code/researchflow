## 0. 结论先行

1. **方向没有跑偏，但节奏有偏。** 做的每一项都在方案里，顺序也符合"先定接口、后做 Agent"。问题是到现在为止，图里**没有任何一个节点**会让模型自主做决定：`run_tool_loop` 和工具注册表都只被单测调用过（`grep run_tool_loop src/researchflow/nodes` 为空）。面试时被追问"你的 Agent 自己决定了什么"，现在仍然答不上来。地基已经比房子大了。
2. **最大的风险是：所有 LLM 相关的结论都只在 Fake 上验证过。** 严格 json_schema、strict 模式下的 `minItems`、原生 tool calling、null 落回默认值、`content: null` 的处理，这些都是按文档写的，从没打过一次真实 Provider。如果真实模型不接受我们的 schema，T-002、T-003 的一部分要返工。这件事越晚做，返工面越大。
3. **下一步要加强的是"可证明的 Agent 能力"，而不是更多的接口形状。** 具体就是三件事，按顺序：真实模型冒烟 → Eval 故障注入集与纯规则基线 → 第一个真正的 Agent（归因回溯）。第 3 轮剩下的 P1 项里，只保留这三件事真正依赖的那几项，其余降级。

## 2. 偏离与风险

### 2.1 节奏偏离：接口超前、能力滞后
- 6 张卡全是"让以后能做 X"的地基。每一张单独看都对，合起来的问题是：**简历方案 §5.2 的 7 条要点里，现在能写数字的只有第 7 条（工程质量）**。第 2、3、4、5 条都依赖真实模型和 Eval，一条都还没有数字。
- 原因：我在 D-004 里把第 3 轮剩余的 P1 项全部排在了 Eval 和 Agent 之前。P1-4（ComputeBackend）、P1-5（predictions）、P1-6（DatasetSpec）是"数据科学流水线的正确性"，对 Agent 岗位加分很少，方案 §3.3 自己也说过这类工作"做了不加分、不做会被问"。

### 2.2 验证偏离：Fake 上全绿不等于真的能跑
已知只在 Fake 上成立、真实模型可能打破的假设：
1. Provider 在 strict 模式下接受 `minItems`、`minLength`、`exclusiveMinimum`（D-005，未实测）。
2. ② 在 json_schema 模式下能一次通过（D-006）。T-003 的反思里写过：e2e 全过不能说明真实模式下 ② 能正常工作，因为 Fake 的 `complete()` 不经过 JSON 解析。
3. 响应里的 `usage` 字段命名和 OpenAI 一致（D-003）。
4. tool calling 的 `arguments` 是合法 JSON 字符串，并行调用时 `tool_call_id` 都能回填上。

### 2.3 流程偏离（小）
- **评审文档的流转换了地方。** Gate 1 原来的约定是测试结果写回 `docs/reviews/gate1/roundN-*.md`；这次全部写在了 `.collab/reviews/`。第 2 轮的"评审结论"一节到现在还空着，第 3 轮没有结果文档。打标签前要补一份 `round3-*.md` 汇总，指向各张 `.collab/reviews`。
- **改造方案本身不在 git 里。** `docs/reviews/resume-pivot/` 一直是未跟踪状态，D-004 说"方向以它为准"，但它可能随时丢。本次审查一起提交。
- **main 比 GitHub 多 43 个提交没 push。** 本地磁盘出问题就全丢了。

### 2.4 没有偏离、值得保留的
- **"静默假阳性"这条主线一直在抓。** T-003 的 `content: null` 被误报为校验失败、T-004 的白名单漏登记会静默丢字段、T-005 的"0 命中返回全部语料"、T-006 的校验结论随安装路径变化、T-007 的"审的不是用的"，都是同一类问题。面试时这是比功能更有区分度的素材（方案 §5.3 最后一行）。
- **协作流程稳定。** CodeBuddy 6 张卡都是一轮通过；唯一的违规（T-004 删了 `runs/*`）通过日志审计发现，并在工具层堵住，之后被拦下 3 次，全是误伤，没有阻碍工作。
